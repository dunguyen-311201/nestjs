## Gap Closures & Integration Enhancements

During this task, two key state-machine event-consumption gaps were identified and closed:

1. **RTS (Return-to-Sender) Event Ingestion**:
   - *Problem*: Although `CourierService` successfully triggered RTS (BR-04) on the 3rd failed attempt and published the `parcel.rts` event, `ParcelEventConsumer` in `apps/order` mapped the subject to `TrackingEventType.RTS` and fed it into `ParcelStateMachine.transition()`. Since RTS is not a regular scan-event detour (and thus not in the FSM transition map), the transition threw an error and dropped the event. The parcel state in the order database never updated to `InTransit` and its direction never flipped to `Reverse_RTS`.
   - *Fix*: Reworked `ParcelEventConsumer` to detect `NATS_SUBJECTS.PARCEL_RTS` specifically, bypass `transition()`, and invoke `ParcelStateMachine.applyRts()` to resolve the new state and direction. Added a new `updateParcelStateAndDirection` method to `IOrderRepository`/`OrderRepository` to update both fields in a single DB write.
   - *Tests*: Added unit tests in `parcel-event.consumer.spec.ts` verifying that `onRts` transitions the state to `InTransit` and direction to `Reverse_RTS` on success, and gracefully drops invalid/out-of-order RTS triggers.

2. **Lost-Suspected Event Ingestion**:
   - *Problem*: While the passive sweep job (UC-15) was marked out of scope for this slice, the downstream consumer in the Order service for `parcel.lost_suspected` was completely missing. The state machine defined `markLostSuspected()` but it was never invoked from NATS.
   - *Fix*: Registered `@EventPattern(NATS_SUBJECTS.PARCEL_LOST_SUSPECTED)` as `onLostSuspected` in `ParcelEventConsumer`, mapping it directly to `ParcelStateMachine.markLostSuspected()`.
   - *Tests*: Added unit tests in `parcel-event.consumer.spec.ts` verifying that `onLostSuspected` marks active parcels as `LOST` and drops terminal/invalid states without throwing.
